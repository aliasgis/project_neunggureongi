# 이슈·커밋·PR 작성 규칙

> 관련: [브랜치 전략](branch-strategy.md) · [버전 정책](versioning.md)

이슈·커밋·PR 제목을 **같은 형식**으로 쓴다.
맨 앞의 대상 버전으로 그 변경이 **어느 버전에 들어가는지**를 `git log` 한 줄에서 바로 알아볼 수 있게 한다.

---

## 1. 제목 형식

```
[<대상버전>] <유형>: <요약> (#<이슈>)
```

```
[1.0] feature: WPS 경사 등급 분류 추가 (#12)
[1.0] doc: 브랜치 전략 문서 추가 (#1)
[1.0.2] fix: PostGIS 연결 시간 초과 처리 (#15)
[1.0.1] release: 버전 1.0.1 출시 준비 (#20)
```

### 1.1 대상 버전

버전 형식은 `x.y.build` 다 ([버전 정책](versioning.md)).

| 작업 | 적는 버전 | 이유 |
|---|---|---|
| `develop` 으로 가는 일반 작업 | **현재 판** `[1.0]` | 어느 출시(build)에 들어갈지는 출시 때 정해진다 |
| 긴급 수정 (`main` 기반 `fix/*`) | **정확한 버전** `[1.0.2]` | 지난 태그의 build + 1 로 바로 출시된다 |
| `release/<x.y>` 안의 커밋 | **정확한 버전** `[1.0.1]` | 출시 번호가 이미 정해져 있다 |
| 분류 전 이슈 | `[미정]` | 버전을 정할 때 제목을 고친다 |

- 현재 판은 `develop` 이 향하는 판이다. 관리자가 판올림을 정하면(예: `1.1`) 그때부터 `develop` 작업은 `[1.1]` 로 쓴다.

### 1.2 유형

브랜치 그룹 이름을 그대로 쓴다.

| 유형 | 쓰는 때 |
|---|---|
| `feature` | 기능 추가·개선 |
| `fix` | 결함 수정 |
| `doc` | 문서만 바꿈 |
| `migration` | 큰 구조 변경·의존성 일괄 상향·데이터 이관 |
| `release` | 출시 준비 (버전 올림 등) |

### 1.3 요약

- 한국어로, **무엇을 했는지**가 드러나게 50자 안팎으로 쓴다.
- `기능업데이트`, `수정`, `wip` 처럼 내용을 알 수 없는 요약은 쓰지 않는다.
- 끝에 마침표를 찍지 않는다.

### 1.4 버전이 바뀌면

작업이 다음 출시로 미뤄지면 **이슈·PR 제목과 마일스톤**을 고친다.
이미 머지된 커밋은 고치지 않는다 — 커밋 제목의 버전은 "어느 출시를 목표로 했는지"를 뜻한다.

| 무엇 | 정본 |
|---|---|
| 이슈가 어느 버전에 들어갈 예정인지 | **마일스톤** (`1.0.1`) |
| 커밋이 실제로 어느 버전에 들어갔는지 | **태그** (`git tag --contains <커밋>`) |

## 2. 이슈

- 제목: `[<대상버전>] <유형>: <요약>` — 이슈 번호는 생략한다.
- 버전을 정하면 **마일스톤**도 같이 지정한다. 분류 전에는 `[미정]` 으로 두고 마일스톤을 비운다.
- 본문: **배경**(왜 필요한가) · **제안**(무엇을 할 것인가) · **할 일**(체크리스트).
  결함은 **재현 방법 · 기대 결과 · 실제 결과 · 환경**을 적는다.
- 이슈 양식이 `.github/ISSUE_TEMPLATE/` 에 있다.

---

## 3. 커밋

```
[1.0] fix: 히트맵 반경을 미터 단위로 계산 (#12)

반경 입력값을 픽셀로 해석해 해상도에 따라 결과가 달라지던 문제.
좌표계 단위(m)로 변환한 뒤 커널을 만들도록 바꿨다.

확인: sample_area 에 RADIUS_M=1000 으로 PIXEL_SIZE_M 50/100 두 번 실행해 같은 범위가 나옴

Refs #12
```

- 제목: §1 형식.
- 본문(필요할 때): **왜** 바꿨는지, **어떻게 확인**했는지. 무엇을 바꿨는지는 diff 가 말해 준다.
- 마지막 줄: `Refs #<이슈>`.
- 한 커밋에는 한 가지 변경만 담는다.

`develop` 은 squash 머지라서 작업 브랜치 안의 커밋은 `develop` 에 하나로 합쳐진다.
작업 브랜치 안에서는 형식을 가볍게 지켜도 되지만, **`main` 에서 갈라진 긴급 `fix/*` 와 `release/*` 의 커밋은 그대로 남으므로** 반드시 지킨다.

---

## 4. PR

- 제목: §1 형식. **squash 머지하면 PR 제목이 그대로 `develop` 의 커밋 제목이 된다.** 이 규칙에서 가장 중요한 곳이다.
- 본문: **연결 이슈 · 무엇을 · 왜 · 확인 방법 · 리뷰어가 볼 곳**. PR 양식이 `.github/pull_request_template.md` 에 있다.
- 이슈 연결:
  - 이 PR 로 이슈가 끝나면 `Closes #<이슈>`
  - 이슈에 다른 할 일이 남으면 `Refs #<이슈>`
  - `develop` 은 기본 브랜치가 아니어서 `Closes` 를 써도 머지할 때 이슈가 자동으로 닫히지 않는다. 머지한 사람이 이슈를 닫는다.
- 마일스톤은 연결 이슈와 같게 지정한다.

---

## 5. 출시와 태그

- `release/*` → `main` PR 제목: `[1.0.1] release: 버전 1.0.1 출시 (#<출시 이슈>)`
- 태그 메시지: `v1.0.1 (YYYY-MM-DD) — <주요 변경 요약>` (판을 올리는 출시면 그 이유를 첫머리에)
- 출시하면 마일스톤 `1.0.1` 을 닫는다. 마일스톤의 이슈 목록이 곧 변경 내역의 뼈대가 된다.

---

## 6. 한눈에

| | 제목 | 본문 끝 | 마일스톤 |
|---|---|---|---|
| 이슈 | `[1.0] feature: 요약` | — | `1.0.1` |
| 커밋 | `[1.0] feature: 요약 (#12)` | `Refs #12` | — |
| PR | `[1.0] feature: 요약 (#12)` | `Closes #12` 또는 `Refs #12` | `1.0.1` |
